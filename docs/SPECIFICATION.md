# Техническое задание
## Bitrix24 Lead Connector

**Версия:** 1.0\
**Тип проекта:** учебный pet-проект, интеграция с CRM\
**Язык разработки:** C#\
**Платформа:** .NET 10 / ASP.NET Core\
**Результат:** работающее приложение, исходный код на GitHub, техническая документация и демонстрация реальной интеграции.

---

## 1. Общая информация

### 1.1. Назначение

Bitrix24 Lead Connector — веб-приложение для автоматической передачи заявок с сайта в CRM Битрикс24 через REST API.

Приложение позволяет пользователю отправить заявку через веб-форму. Серверная часть проверяет полученные данные, отправляет запрос к API Битрикс24 и создаёт новый лид.

Дополнительно реализуется получение списка лидов из CRM для демонстрации двустороннего обмена данными.

### 1.2. Цель разработки

Продемонстрировать практические навыки:

- Разработки REST API на ASP.NET Core.
- Интеграции со сторонними системами через HTTP.
- Использования входящих вебхуков Битрикс24.
- Сериализации и десериализации JSON.
- Обработки ошибок стороннего API.
- Работы с конфигурацией и секретами приложения.
- Написания тестов и технической документации.

### 1.3. Бизнес-сценарий

Небольшая компания использует Битрикс24 для обработки клиентских обращений.

На сайте компании есть форма обратной связи. Раньше менеджер вручную переносил данные заявок в CRM.

После внедрения Bitrix24 Lead Connector заявки автоматически поступают в Битрикс24, где менеджер может приступить к их обработке.

### 1.4. Границы проекта

**В обязательную версию (MVP) входят:**

1. Веб-форма отправки заявки.
2. Backend API на ASP.NET Core.
3. Создание лида в Битрикс24.
4. Получение списка лидов из Битрикс24.
5. Проверка корректности входных данных.
6. Обработка ошибок интеграции.
7. Логирование.
8. Swagger/OpenAPI.
9. Автоматические тесты ключевой логики.
10. README и демонстрация работы.

**Не входят в MVP:**

- Регистрация и авторизация обычных пользователей.
- Собственная база данных.
- Редактирование и удаление лидов.
- Сложная административная панель.
- Микросервисная архитектура.
- Очереди сообщений.
- OAuth 2.0.
- Публикация приложения в Маркетплейсе Битрикс24.

## 3. Архитектура

### 3.1. Общая схема

```text
Пользователь
     |
     v
Веб-форма (HTML + JS)
     |
     | POST /api/leads
     v
ASP.NET Core Minimal API
     |
     | Валидация
     v
LeadService
     |
     | Формирование запроса
     v
Bitrix24Client (HttpClient)
     |
     | HTTPS / REST API
     v
Битрикс24 CRM
     |
     v
Созданный лид
     |
     v
Ответ с ID лида
     |
     v
Уведомление пользователя
```

При получении списка лидов backend обращается к Битрикс24, преобразует ответ в собственную модель и возвращает данные через `GET /api/leads`.

### 3.2. Основные компоненты

**Frontend**

Отвечает за отображение формы, клиентскую проверку, отправку заявки и уведомление о результате.

**API Endpoints**

Принимает HTTP-запросы, проверяет входные модели, вызывает сервис приложения и возвращает HTTP-ответы.

**LeadService**

Содержит прикладную логику: подготовку названия лида, нормализацию данных, взаимодействие с клиентом Битрикс24 и преобразование результата.

**Bitrix24Client**

Отвечает исключительно за REST-запросы к Битрикс24, сериализацию JSON, чтение ответов и обработку ошибок внешней системы.

**Configuration**

Хранит настройки интеграции: URL вебхука, тайм-ауты и другие параметры.

### 3.3. Требования к архитектуре

- Использовать Dependency Injection.
- Работу с Битрикс24 вынести в отдельный класс.
- Не обращаться к Битрикс24 непосредственно из обработчиков HTTP.
- Не хранить URL вебхука непосредственно в исходном коде.
- Использовать асинхронные методы и `CancellationToken`.
- Не создавать собственную базу данных.

Не требуется внедрять полноценную Clean Architecture, CQRS или Mediator.

## 4. Функциональные требования

### FR-01. Веб-форма заявки

По адресу `/` должна открываться страница отправки заявки.

Форма содержит:

| Поле | Тип | Обязательное |
|---|---|---|
| Имя | text | Да |
| Телефон | tel | Да |
| Комментарий | textarea | Нет |
| Кнопка «Отправить заявку» | button | — |

Требования:

1. Все поля имеют понятные подписи.
2. Обязательные поля проверяются перед отправкой.
3. При отправке кнопка временно блокируется.
4. После успешной отправки выводится подтверждение.
5. При ошибке выводится понятное сообщение.
6. При неудачной отправке введённые данные сохраняются в форме.
7. Повторное нажатие во время выполнения одного запроса не создаёт дополнительный запрос.

Сложная стилизация не требуется.

### FR-02. Проверка входных данных

Валидация выполняется как на frontend, так и на backend.

| Поле | Ограничения |
|---|---|
| name | От 2 до 80 символов после удаления пробелов по краям |
| phone | От 10 до 15 цифр; допускаются `+`, пробелы, дефисы и скобки |
| comment | Необязательное, максимум 1000 символов |

Правила:

- Имя не может состоять исключительно из пробелов.
- Номер нормализуется: пробелы, скобки и дефисы удаляются.
- Начальный `+` сохраняется.
- Номер с посторонними символами отклоняется.
- Комментарий может быть пустым.
- Запрос с некорректными данными не отправляется в Битрикс24.
- Backend возвращает информацию об ошибках соответствующих полей.

### FR-03. Создание лида в Битрикс24

После получения корректной заявки приложение должно:

1. Сформировать заголовок лида: `Заявка с сайта — {имя}`.
2. Подготовить поля CRM.
3. Выполнить запрос к Битрикс24 методом `crm.item.add`.
4. Передать `entityTypeId = 1` (тип объекта «Лид»).
5. Получить идентификатор созданного лида из `result.item.id`.
6. Вернуть клиенту результат создания.

**Сопоставление полей:**

| Поле приложения | Поле Битрикс24 |
|---|---|
| Сгенерированный заголовок | `title` |
| name | `name` |
| phone | `fm` с `typeId = PHONE` |
| comment | `comments` |

Телефон передаётся с типом значения `WORK`.

Пример запроса к Битрикс24:

```json
{
  "entityTypeId": 1,
  "fields": {
    "title": "Заявка с сайта — Иван",
    "name": "Иван",
    "comments": "Перезвоните вечером",
    "fm": [
      {
        "typeId": "PHONE",
        "valueType": "WORK",
        "value": "+79991112233"
      }
    ]
  }
}
```

При успешном выполнении ID лида извлекается из ответа CRM.

### FR-04. Получение списка лидов

Приложение должно поддерживать получение существующих лидов через метод `crm.item.list`.

Требования:

- Получать данные непосредственно из CRM.
- Не хранить полученный список в собственной БД.
- Возвращать данные в упрощённом формате.
- Поддерживать начальную позицию выборки `start`.
- Поддерживать получение следующей страницы.
- Не возвращать клиенту полный исходный ответ Битрикс24.
- При чтении телефонных номеров учитывать структуру `fm`.

Отображаемые поля:

- ID лида.
- Название.
- Имя клиента.
- Телефон.
- Комментарий.
- Дата создания.

Для MVP этот endpoint должен регистрироваться **только в Development-окружении**, поскольку данные CRM могут содержать персональную информацию. В production получение списка без отдельной авторизации запрещено.

### FR-05. Обработка ошибок

Сервис должен корректно реагировать на следующие ситуации:

| Ситуация | Действие |
|---|---|
| Некорректная заявка | Вернуть ошибки валидации |
| Неверный или просроченный вебхук | Вернуть ошибку интеграции |
| Недостаточно прав в CRM | Вернуть ошибку интеграции |
| Битрикс24 недоступен | Сообщить о временной недоступности |
| Превышен тайм-аут | Завершить запрос с ошибкой |
| Некорректный JSON от CRM | Записать диагностическую ошибку |
| Ответ CRM содержит поле `error` | Обработать как ошибку, независимо от HTTP-статуса |
| Успешный HTTP-ответ без ожидаемого ID | Вернуть ошибку интеграции |

Нельзя показывать пользователю секретный URL, токен или полный технический ответ внешней системы.

Автоматические повторные запросы на создание лида не выполняются в MVP, поскольку это может приводить к дублированию заявок.

### FR-06. Логирование

Использовать стандартный `ILogger`.

Записывать следующие события:

- Начало обработки заявки.
- Успешное создание лида с его ID.
- Ошибка валидации без записи персональных данных.
- Ошибка REST API.
- Превышение времени ожидания.
- Ошибка десериализации ответа.
- Получение списка лидов.

Уровни логирования:

| Уровень | Назначение |
|---|---|
| Information | Успешные операции |
| Warning | Ошибки валидации, ограничения API |
| Error | Сбои внешней интеграции |

В логах запрещено записывать токены, полный URL вебхука, телефон, имя клиента и содержимое комментария.

### FR-07. Swagger/OpenAPI

Backend должен предоставлять документацию API в Development-окружении.

Необходимо:

1. Описать маршруты и HTTP-методы.
2. Описать модели запросов.
3. Указать успешные и ошибочные ответы.
4. Обеспечить возможность тестирования API без HTML-формы.

### FR-08. Проверка состояния сервиса

Добавить маршрут `GET /health`, который возвращает `200 OK`, если само приложение запущено и готово принимать запросы.

Проверка `/health` не должна обращаться к Битрикс24 и не подтверждает доступность CRM.

## 5. Контракты собственного REST API

### 5.1. POST /api/leads

**Назначение:** создание нового лида.

**Content-Type:** `application/json`

Пример запроса:

```json
{
  "name": "Иван",
  "phone": "+79991112233",
  "comment": "Хочу узнать стоимость услуги"
}
```

Успешный ответ — `201 Created`:

```json
{
  "success": true,
  "leadId": 123,
  "message": "Заявка успешно отправлена"
}
```

Ошибка валидации — `400 Bad Request`:

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "errors": {
    "name": [
      "Имя должно содержать от 2 до 80 символов"
    ],
    "phone": [
      "Некорректный номер телефона"
    ]
  }
}
```

Ошибка интеграции — `502 Bad Gateway`:

```json
{
  "success": false,
  "code": "BITRIX_API_ERROR",
  "message": "Не удалось передать заявку в CRM"
}
```

Дополнительные статусы:

- `429 Too Many Requests` — ограничение числа запросов.
- `503 Service Unavailable` — внешняя система недоступна.
- `504 Gateway Timeout` — время ожидания Битрикс24 истекло.

### 5.2. GET /api/leads

**Назначение:** получение списка лидов CRM.

Доступен только в Development.

Пример:

```http
GET /api/leads?start=0
```

Запрос к Битрикс24 выполняется методом `crm.item.list` с параметрами:

```json
{
  "entityTypeId": 1,
  "select": ["*"],
  "start": 0
}
```

Успешный ответ — `200 OK`:

```json
{
  "items": [
    {
      "id": 123,
      "title": "Заявка с сайта — Иван",
      "name": "Иван",
      "phone": "+79991112233",
      "comments": "Хочу консультацию",
      "createdTime": "2026-11-10T12:00:00+03:00"
    }
  ],
  "total": 1,
  "nextStart": null
}
```

`nextStart` содержит позицию следующей страницы из ответа Битрикс24 либо `null`, если следующей страницы нет.

Максимальный размер страницы определяется API Битрикс24. Для MVP достаточно стандартной выборки до 50 элементов за запрос.

### 5.3. GET /health

Успешный ответ — `200 OK`:

```json
{
  "status": "healthy"
}
```

## 6. Интеграция с Битрикс24

### 6.1. Предварительные условия

Для запуска необходимы:

1. Тестовый портал Битрикс24.
2. Действующий доступ к REST API.
3. Классический режим CRM с поддержкой лидов.
4. Пользователь с правом создавать и читать лиды.
5. Входящий вебхук со scope `crm`.

Использовать только собственный тестовый портал, не рабочую CRM работодателя.

### 6.2. Авторизация

Для MVP используется входящий вебхук Битрикс24.

Формат базового URL:

```text
https://portal.bitrix24.ru/rest/{userId}/{webhookToken}/
```

Все обращения к CRM выполняются на сервере.

URL вебхука не должен передаваться в JavaScript, HTML, ответы клиенту или публичный репозиторий.

### 6.3. Используемые методы

| Метод | Назначение |
|---|---|
| `crm.item.add` | Создать лид |
| `crm.item.list` | Получить список лидов |
| `profile` | Проверить работоспособность вебхука на этапе настройки |

Для операций с лидами передавать `entityTypeId = 1`.

Пути вызова относительно базового URL вебхука:

```text
crm.item.add.json
crm.item.list.json
profile.json
```

Запросы к CRM выполняются по HTTPS методом POST с JSON-телом там, где требуются параметры.

### 6.4. Конфигурация

Использовать Options Pattern.

Пример структуры настроек:

```json
{
  "Bitrix24": {
    "WebhookBaseUrl": "",
    "TimeoutSeconds": 10
  }
}
```

В публичном `appsettings.json` URL вебхука должен оставаться пустым.

Реальный URL передаётся через .NET User Secrets или переменную окружения:

```text
Bitrix24__WebhookBaseUrl
```

При запуске необходимо проверять корректность конфигурации.

Если URL не задан или некорректен, приложение должно сообщать о конфигурационной ошибке при запуске, а не при первой заявке.

## 7. Нефункциональные требования

### 7.1. Производительность

- Все обращения к Битрикс24 должны быть асинхронными.
- Время ожидания одного запроса к CRM по умолчанию — 10 секунд.
- Приложение не должно блокировать потоки в ожидании ответа API.
- Обработка отдельной заявки не должна требовать обращения к БД.

### 7.2. Безопасность

- Использовать HTTPS для обращений к CRM.
- Не хранить секреты в Git.
- Не выводить секретный URL в логах.
- Не раскрывать внутренние исключения пользователям.
- Выполнять серверную валидацию всех полей.
- Ограничить размер входного JSON разумным пределом, например 8 КБ.
- Не разрешать произвольные URL для внешних запросов.
- Ограничить количество запросов к `POST /api/leads`, например пятью запросами в минуту на IP для демонстрационного режима.
- Не публиковать `GET /api/leads` без авторизации.
- Не включать реальные персональные данные в документацию или тесты.

Проект рассчитан на локальную демонстрацию. Для публичного размещения потребуется дополнительная защита от спама и злоупотреблений.

### 7.3. Надёжность

- Сбой CRM не должен приводить к аварийному завершению backend.
- Ошибки HTTP и ошибки бизнес-уровня API должны обрабатываться отдельно.
- Отмена клиентского запроса должна поддерживаться через `CancellationToken`.
- При неоднозначном результате отправки не следует автоматически создавать заявку повторно.
- Все ошибки интеграции должны иметь диагностические записи в журнале.

### 7.4. Поддерживаемость

- Не дублировать код формирования HTTP-запросов.
- Использовать модели DTO вместо передачи произвольных JSON-объектов между слоями.
- Названия классов и методов должны отражать их назначение.
- Не смешивать логику HTTP API и интеграцию с CRM.
- Основная логика должна тестироваться без подключения к реальному Битрикс24.

## 9. Требования к тестированию

### 9.1. Unit-тесты

Использовать xUnit.

Обязательные сценарии:

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| T-01 | Корректная заявка | Подготовлен запрос создания лида |
| T-02 | Пустое имя | Ошибка валидации |
| T-03 | Имя длиннее 80 символов | Ошибка валидации |
| T-04 | Некорректный телефон | Ошибка валидации |
| T-05 | Корректный телефон с пробелами | Номер нормализован |
| T-06 | Комментарий длиннее 1000 символов | Ошибка валидации |
| T-07 | Битрикс24 вернул ID | Сервис возвращает ID |
| T-08 | Битрикс24 вернул ошибку | Возвращается ошибка интеграции |
| T-09 | HTTP 200 с полем `error` | Ответ считается ошибочным |
| T-10 | Истёк тайм-аут | Ошибка корректно обрабатывается |
| T-11 | Некорректный JSON от CRM | Ошибка десериализации обработана |
| T-12 | Ответ без `result.item.id` | Не возвращается ложный успех |
| T-13 | Успешный список лидов | Данные преобразованы в DTO |
| T-14 | Пустой список лидов | Возвращается пустой массив |
| T-15 | Следующая страница | Корректно передаётся `nextStart` |

### 9.2. Изоляция тестов

Автоматические тесты не должны создавать реальные лиды.

Для тестирования использовать подмену HTTP-ответов через `HttpMessageHandler` или мокирование интерфейса клиента.

Настоящий портал используется только при ручном интеграционном тестировании.

### 9.3. Ручное интеграционное тестирование

Необходимо:

1. Запустить приложение локально.
2. Открыть веб-форму.
3. Ввести имя, телефон и комментарий.
4. Отправить заявку.
5. Убедиться, что отображается успешный ответ.
6. Открыть тестовый портал Битрикс24.
7. Найти созданный лид.
8. Сравнить значения полей с данными формы.
9. Проверить `GET /api/leads` в Swagger.
10. Проверить поведение при некорректной заявке и неработающем вебхуке.

Эти задачи необязательны и не влияют на приёмку первой версии.

### BONUS-01. Исходящий вебхук Битрикс24

Реализовать обработчик:

```http
POST /api/webhooks/bitrix24
```

Настроить исходящий вебхук на событие создания лида `ONCRMLEADADD`.

При получении события приложение должно:

1. Проверить токен исходящего вебхука.
2. Получить ID созданного лида.
3. Записать событие в лог.
4. Вернуть подтверждение обработки.

Для реализации потребуется публичный HTTPS-адрес обработчика или временный HTTPS-туннель. Секрет исходящего вебхука хранится отдельно от URL входящего.
