# Архитектура

Один ASP.NET Core процесс обслуживает статическую страницу и Minimal API. Базы данных и отдельного frontend-сервера нет.

## Ответственность компонентов

| Компонент | Обязанности |
|---|---|
| `LeadEndpoints` | Bounded read до 8192 байт, Content-Type, JSON, параметры списка, HTTP-коды и описание OpenAPI |
| `LeadValidation` | Длина имени после Trim, формат и число ASCII-цифр телефона, длина исходного комментария |
| `LeadService` | Проверка заявки, нормализация, заголовок, mapping DTO CRM и своего API |
| `IBitrix24Client` / `Bitrix24Client` | JSON через HTTPS, разбор envelope, проверка результата, классификация интеграционных сбоев |
| `Bitrix24OptionsValidator` | Fail-fast проверка HTTPS URL, пути вебхука и тайм-аута; ошибки без секретного значения |
| `ApiExceptionHandler` | Безопасный формат ошибок, поддержка отмены клиентом |
| `Program` | DI, HttpClient, middleware, ограничения и регистрация Development-маршрутов |

## Поток создания

1. Форма проверяет имя, телефон и комментарий, блокирует кнопку и устанавливает `sending`.
2. API проверяет JSON и лимиты. Rate limiter отклоняет шестую попытку с одного IP в минутном окне, включая некорректные попытки.
3. Сервис валидирует модель. Имя обрезается по краям; из телефона удаляются пробелы, скобки и дефисы; начальный `+` сохраняется. Комментарий проверяется до Trim, затем обрезается по краям.
4. Клиент отправляет один POST `crm.item.add.json`, `entityTypeId = 1`, поля `title`, `name`, `comments`, `fm`.
5. Клиент читает `result.item.id`, проверяет положительный ID и возвращает его сервису.
6. API возвращает `201`, форма показывает ID. Форма очищается только после подтверждённого успеха.

## Чтение и пагинация

`crm.item.list.json` получает `select: ["*"]`, поскольку `fm` нельзя запросить отдельным полем `select`. На выходе API оставляет ID, название, имя, первый PHONE из `fm`, комментарий и дату. `total` и `next` берутся из верхнего уровня ответа CRM. Отсутствующий `next` превращается в `nextStart: null`.

## Ошибки и отмена

- `error` в envelope означает ошибку независимо от HTTP-статуса, включая пустое или null значение этого поля.
- Ошибочный HTTP-статус классифицируется даже при невалидном JSON.
- Неверный JSON / отсутствие положительного ID / неправильная структура списка означают интеграционную ошибку, а не успех.
- `HttpClient.Timeout` отличается от отмены запроса пользователем: тайм-аут становится 504, пользовательская отмена распространяется дальше (499 при обработке прерванного запроса).
- Повторных запросов нет. Потеря ответа после сохранения в CRM не доказывает, что лид отсутствует.

## Защита данных

URL вебхука есть только в конфигурации backend. Клиент не принимает адрес CRM из HTTP-запроса; используются два фиксированных относительных метода. Автоматические HTTP-перенаправления отключены. Сертификат проверяется стандартным TLS-стеком.

Стандартные HttpClient-логгеры удалены, потому что в их события попадает полный URI с секретом в пути. При интеграционных сбоях журналируются только фиксированный метод, HTTP-статус и классификация. Исключения транспорта, исходный JSON, `error_description`, имя, телефон и комментарий не журналируются. Ответы API имеют `Cache-Control: no-store`. Middleware ошибок работает и в Development; техническая страница исключения не используется для ответов приложения.

JSON ограничен 8 КБ в Kestrel и в endpoint, в том числе без Content-Length. Ответы CRM ограничены буфером 8 МБ. URL проверяется по формату `/rest/{userId}/{token}/`, HTTPS, стандартному порту и DNS-имени; допускаются собственные домены порталов.

Публикация Development запрещена сценарием использования. Регистрация GET и Swagger отсутствует в любых других окружениях; это проверяется тестами для Production и Staging.
